# SkyBook: measured results (owner's machine, 2026-11-07)

**Environment:** Windows + Docker Desktop, 8 vCPU / 7.6 GB RAM visible to Docker. All services, Kafka (apache/kafka:3.8.0),
PostgreSQL 16 and Redis 7 ran in Docker Compose on the same machine. The bridge test used **real Amazon SQS (us-east-2)**.
Produced by `scripts/run-benchmarks.ps1` and the bridge outage test; the raw JSON is in `load-tests/results/`.

## Flight search: 1,000,000 flights, k6, 20 VUs × 60 s each, popular-routes mix

| Variant | Requests | Throughput | p50 | p95 | p99 | Cache hit rate | Errors |
|---|---|---|---|---|---|---|---|
| No index | 2,094 | 35 req/s | 525.3 ms | 1,020.7 ms | 1,257.7 ms | – | 0.0 % |
| Composite index | 67,186 | 1,120 req/s | 16.6 ms | 28.4 ms | 37.7 ms | – | 0.0 % |
| Index + Redis cache | 98,473 | 1,641 req/s | 9.63 ms | 25.5 ms | 35.8 ms | **89.1 %** | 0.0 % |

- The composite index cut p95 **36×** under load (1,020.7 → 28.4 ms) and raised throughput **32×**.
- The Redis cache took p95 to **25.5 ms** (**40×** better than no index), and compared with the index alone it cut p50 by 42 % and added 47 % throughput.
- `EXPLAIN ANALYZE` on 50 random routes, single query: p95 **73.3 ms** with a sequential scan, **0.28 ms** with the composite index (**266×**).
  The under-load numbers are larger because 20 concurrent sequential scans compete for the same CPU and disk.

## Idempotency: k6, 100 identical concurrent requests with one `Idempotency-Key`

**1 stored booking, 0 duplicates.** The other 99 requests got 62 replays of the saved response and 37 × `409 Conflict`, with 0 unexpected statuses.
The integration test (50 concurrent requests on real PostgreSQL) gives the same result: 1 booking.

## 10× booking spike: k6 (5/s → 50/s for 60 s) + spike monitor

| Metric | Value |
|---|---|
| Booking requests | 3,575 bookings (+31 setup calls) at 5/s → **50/s** for 60 s, **0.0 % errors** |
| Booking API p95 during the spike | 22.6 ms |
| Events produced to Kafka | 17,875 |
| Peak consumer lag, all groups | 3,092 messages, almost all in `payment` (3,070) |
| All consumers caught up | **161 s** after the last booking request |
| Messages left unconsumed | **0** |
| Bookings that reached a final saga state | **3,575 / 3,575** |

The bottleneck is the payment consumer. Its mock provider adds 200 ms per charge, and with 3 partitions it processes about 15 charges per second at most.
The booking API stayed fast (p95 22.6 ms) because the outbox and Kafka absorb the burst instead of the HTTP path.
Two scaling levers: more partitions with more payment replicas, or concurrent charges within a partition, since payments don't need per-flight ordering.

## Resume bullets (measured values)

**SkyBook: Flight Booking Microservices** | Node.js, TypeScript, Kafka, AWS (SQS, CDK), PostgreSQL, Redis, Docker, Kubernetes, Prometheus, Grafana

- Built a 5-service flight booking platform in **Node.js/TypeScript** with database-per-service and a **Kafka** saga that releases held seats when payment fails, **deployed on Kubernetes with Helm** (kind) and Docker Compose.
- Made `POST /bookings` idempotent with stored idempotency keys and saved responses, producing **0 duplicate bookings across 100 concurrent retried requests** under k6 load, and verified the same with PostgreSQL integration tests.
- Cut p95 flight-search latency from **1,021 ms to 25.5 ms (40×)** on a 1M-row table using a composite index (verified with `EXPLAIN ANALYZE`: 73 ms → 0.28 ms) and a Redis cache with event-driven invalidation, reaching an **89 % hit rate** and 1,641 req/s under k6 load.
- Absorbed a **10× traffic spike** (3,575 bookings, 17,875 events) with **zero lost messages** and 0 % errors, using a transactional outbox, exponential-backoff retry topics, and a dead-letter topic with a replay tool; all consumers caught up within 161 s, monitored through Prometheus/Grafana alerts on consumer lag.
- Built a **Node.js Kafka → AWS SQS bridge** that commits Kafka offsets only after AWS confirms each batch and pauses consumption during outages, delivering **1,200/1,200 events with no loss** through a 2-minute network outage against real Amazon SQS.
