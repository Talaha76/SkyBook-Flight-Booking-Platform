# Benchmarks

> **Resume numbers are in [results-2026-11-07.md](results-2026-11-07.md)** (owner's machine, real AWS SQS). This file keeps the earlier development-sandbox runs.

All numbers below were **measured**, not estimated. They come from the development sandbox
(2 vCPU, 7.8 GB RAM, Linux, PostgreSQL 16, Redis 7, everything on one machine). Re-run them
on your own machine before you quote them on a resume.

## 1. Search query: no index vs. composite index (1,000,000 flights)

Command (seed 1M rows into a separate database, then benchmark):

```powershell
docker compose exec postgres psql -U postgres -c "CREATE DATABASE skybook_bench"
docker compose run --rm -e FLIGHTS_DATABASE_URL=postgres://postgres:postgres@postgres:5432/skybook_bench -e INVENTORY_DATABASE_URL=postgres://postgres:postgres@postgres:5432/skybook_bench seed node dist/scripts/seed-flights.js --count 1000000
docker compose run --rm -e FLIGHTS_DATABASE_URL=postgres://postgres:postgres@postgres:5432/skybook_bench seed node dist/scripts/explain-benchmark.js --runs 50
```

Query: `WHERE origin = $1 AND destination = $2 AND departure_date = $3 ORDER BY departure_time LIMIT 100`,
50 random routes per variant. The times are PostgreSQL execution times from `EXPLAIN (ANALYZE, BUFFERS)`.

| Variant | Plan | p50 ms | p95 ms | p99 ms |
|---|---|---|---|---|
| no index | Limit → Gather Merge → Sort → **Seq Scan** | 61.953 | 82.387 | 91.662 |
| `idx_flights_route_date (origin, destination, departure_date, departure_time)` | Limit → Sort → Bitmap Heap Scan → **Bitmap Index Scan** | 0.084 | 0.583 | 0.638 |

**p95 speed-up: about 141×.** Seeding 1,000,000 flights (flights + seat inventory) took 27.9 s.

## 2. End-to-end search through the gateway: cache off vs. on (1M rows, indexed)

The test sent 4,000 requests from 20 concurrent clients through the gateway (JWT/rate-limit middleware → flight-search → Postgres/Redis), using a skewed
"popular routes" mix: 20 airports with squared-random selection and 1–30 days out. Load was generated by a Node fetch loop on the
**same 2-vCPU machine**, so the client, gateway, service, Postgres and Redis all competed for CPU.

| Cache | Throughput | p50 ms | p95 ms | p99 ms | Hit rate |
|---|---|---|---|---|---|
| off (`SEARCH_CACHE_ENABLED=false`) | 599 req/s | 31.34 | 51.57 | 67.68 | — |
| on (Redis cache-aside, 60 s TTL) | 733 req/s | 25.18 | 47.83 | 67.08 | 39.1 % |

Interpretation: once the index exists, a search hits Postgres in under 1 ms, so the cache mainly saves
DB connections and CPU (+22 % throughput). The hit rate is modest because this mix produces about 12,000 distinct
route/date keys against a 60 s TTL. Raise the skew or the TTL to see higher hit rates. For the guide's
k6 version, run `docker compose --profile tools run --rm k6 run /scripts/search.js` (not yet run, because k6 wasn't available in the sandbox).

## 3. Correctness under concurrency (integration tests, real PostgreSQL)

| Test | Result |
|---|---|
| 50 identical concurrent `POST /bookings` with one Idempotency-Key | **1 booking**, 1 outbox event, 49 replays of the saved response, 0 duplicates |
| 200 concurrent seat holds on a 150-seat flight, pessimistic `SELECT … FOR UPDATE` | **150 held / 50 SOLD_OUT**, available = 0, 746 ms |
| 200 concurrent seat holds on a 150-seat flight, optimistic versioned `UPDATE` | **150 held / 50 SOLD_OUT**, available = 0, 483 ms |
| Same `BookingRequested` event delivered twice | state changed once, the second delivery was reported as `duplicate` |

Re-run on the owner's machine (Windows, Docker Desktop, `docker compose --profile tools run --rm tests`, 2026-11-07): race → 1 created / 49 replays / 0 duplicates; pessimistic **671 ms**, optimistic **689 ms**, both 150 held / 50 rejected.

The lock-strategy timings above come from one run each. Treat them as indicative, and benchmark
both strategies on your own hardware (`INVENTORY_LOCK_STRATEGY=pessimistic|optimistic`).

## 4. Kafka → SQS bridge under a 2-minute AWS outage

`scripts/bridge-outage-test.ts` (fake SQS returning 503 for every call during the outage window), sandbox run:
300 bookings through the gateway at 10/s, with the outage starting after 75 bookings.

| Metric | Run 1 (per-partition cooldown) | Run 2 (resume all partitions on first success) |
|---|---|---|
| Bookings accepted | 300 / 300 | 300 / 300 |
| Bridge paused (circuit breaker) | yes | yes |
| Peak backlog held in Kafka | 976 events | 978 events |
| Time to drain after AWS restored | 41.1 s | **1.0 s** |
| Events produced to Kafka / unique received in SQS | 1,200 / 1,200 | **1,200 / 1,200** |
| Duplicates delivered | 0 | 0 |

Run 1 showed that each paused partition waited out its own cooldown, which could be up to 60 s. The fix resumes every paused
partition as soon as any send succeeds. The drain time is measured at 1-second polling resolution.
